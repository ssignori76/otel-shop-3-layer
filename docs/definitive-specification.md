# Commerce Synthetic Application
## Definitive Architecture, Implementation and Test Specification

**Status:** approved development baseline  
**Document scope:** functional requirements, solution architecture, implementation standards, containerization, observability, testing and release gates  
**Deployment baseline:** Docker Compose  
**Application runtime:** Java 21 LTS  
**Initial observability backend:** Jaeger through OTLP  

# 1. Purpose

This document is the single normative specification for the implementation of a distributed synthetic e-commerce application. It supersedes the earlier single-process simulator design.

The application must exercise real HTTP, JDBC and AMQP communication so that distributed traces are generated by the actual runtime interactions among independently deployed components. The application is intentionally small, deterministic and suitable for observability tests. It is not intended to implement a production commerce platform.

# 2. Objectives

The solution must:

- generate a complete e-commerce journey at a configurable interval;
- execute real HTTP requests through a web tier and an API Gateway;
- execute real database operations against MySQL;
- publish and consume real messages through RabbitMQ;
- propagate W3C Trace Context across HTTP and AMQP boundaries;
- generate OpenTelemetry traces from independent processes;
- support deterministic normal and failure scenarios;
- validate all traces against Jaeger during the initial test phase;
- build, test and run entirely inside Docker containers;
- publish independent application images to a container registry;
- include all source code, Dockerfiles, Compose files, tests and documentation in one Git repository.

# 3. Non-goals for the initial release

The following capabilities are excluded from the first release:

- Kubernetes deployment;
- public-cloud managed services;
- horizontally scaled services;
- concurrent journey generation;
- user authentication and authorization;
- distributed transactions;
- transactional outbox;
- service discovery;
- automatic HTTP retries;
- service mesh;
- production-grade Jaeger deployment;
- metrics and log validation as release-blocking signals;
- load or performance testing.

# 4. Executive architecture decision

The implementation uses a distributed synthetic application rather than an in-process trace simulator.

# 7. Functional workflow

## 7.1 Normal journey

1. The Journey Generator creates `run_id` and `journey_id` UUID values.
2. It sends the initial HTTP request to Apache HTTP Server.
3. Apache forwards `/api/*` to the API Gateway without removing `traceparent`, `tracestate`, `baggage`, `x-run-id`, `x-journey-id` or authorized scenario headers.
4. The API Gateway routes the cart operation to Cart Service.
5. Cart Service inserts a cart record into `cart_db` and returns HTTP 201.
6. The API Gateway retrieves the cart through Cart Service.
7. Checkout Service loads the cart state required for checkout.
8. Checkout Service calls Merchant Service for payment authorization.
9. Merchant Service returns a successful authorization.
10. Checkout Service persists the order in `checkout_db`.
11. Checkout Service publishes an order message to RabbitMQ using publisher confirms.
12. Checkout Service updates the order state to `PUBLISHED` after a positive confirm.
13. Checkout returns HTTP 202 and the API Gateway propagates the response.
14. Fulfillment Service consumes the message.
15. Fulfillment Service persists fulfillment in `fulfillment_db`.
16. Fulfillment Service acknowledges the RabbitMQ message only after the MySQL transaction commits.

## 7.2 State model

The canonical journey states are:

`STARTED -> PAGE_LOADED -> CART_CREATED -> CART_READ -> PAYMENT_AUTHORIZED -> ORDER_PUBLISHED -> FULFILLED`

Failure terminal states include:

- `CHECKOUT_FAILED`;
- `DB_TIMEOUT`;
- `MERCHANT_TIMEOUT`;
- `PAYMENT_AUTHORIZED_NOT_PUBLISHED`;
- `FULFILLMENT_FAILED`;
- `INTERNAL_FAILURE`.

# 8. Journey scheduling

The Journey Generator uses fixed-delay scheduling.

| Property | Default | Constraint |
|---|---:|---|
| `GENERATOR_ENABLED` | `true` | Boolean |
| `GENERATOR_INTERVAL_SECONDS` | `10` | Integer, minimum 1 |
| `GENERATOR_INITIAL_DELAY_SECONDS` | `5` | Integer, minimum 0 |
| `GENERATOR_MAX_IN_FLIGHT` | `1` | Fixed to 1 in the initial release |
| `GENERATOR_REQUEST_TIMEOUT_SECONDS` | `30` | Positive integer |
| `GENERATOR_MAX_JOURNEYS` | `0` | 0 means continuous execution |
| `GENERATOR_STOP_ON_UNEXPECTED_ERROR` | `false` | Boolean |

The delay begins after the initial synchronous HTTP request completes. The next journey must not start before the configured delay expires. A default ten-second interval is selected to limit system load.

The asynchronous fulfillment may complete during the delay. The initial release does not poll fulfillment before scheduling the next journey. Queue depth and unique journey identifiers prevent data ambiguity.

# 9. HTTP contracts

All business APIs use JSON and publish OpenAPI 3.1 definitions. Every request validates inputs using Jakarta Bean Validation.

## 9.1 Required headers

| Header | Purpose | Propagation |
|---|---|---|
| `traceparent` | W3C trace context | All HTTP and RabbitMQ boundaries |
| `tracestate` | Vendor trace state | Preserve when present |
| `baggage` | Optional propagation fields | Preserve only approved keys |
| `x-run-id` | Run correlation UUID | All business calls and AMQP message |
| `x-journey-id` | Journey correlation UUID | All business calls and AMQP message |
| `x-simulation-scenario` | Selected scenario | Internal network only |
| `x-simulation-enabled` | Scenario activation | Internal network only |

Scenario headers must not be accepted from an untrusted external network in a future exposed deployment. In Docker Compose they are accepted only from the Journey Generator path.

## 9.2 API endpoints

| Component | Method and path | Success response |
|---|---|---|
| Apache / Gateway | `POST /api/journeys` | `202 Accepted` |
| Cart Service | `POST /internal/carts` | `201 Created` |
| Cart Service | `GET /internal/carts/{cartId}` | `200 OK` |
| Checkout Service | `POST /internal/checkouts` | `202 Accepted` |
| Merchant Service | `POST /internal/payments/authorize` | `200 OK` |
| Services | `GET /actuator/health/liveness` | `200` when alive |
| Services | `GET /actuator/health/readiness` | `200` when dependencies are ready |

## 9.3 Error response

All synchronous errors use a stable JSON envelope containing:

- `timestamp` in RFC 3339 UTC;
- `status`;
- `error_code`;
- `message` without secrets or stack traces;
- `run_id`;
- `journey_id`;
- `trace_id` when available.

# 10. API Gateway requirements

Spring Cloud Gateway must:

- define static routes through external configuration;
- propagate W3C and approved business headers;
- add no automatic retry;
- apply explicit connect and response timeouts;
- expose Actuator liveness and readiness;
- reject unknown public routes;
- return the upstream status without converting expected 4xx/5xx responses;
- avoid logging authorization data or request bodies;
- be instrumented through the OpenTelemetry Java Agent.

Initial routes:

- `/api/journeys/**` to Checkout orchestration as defined by the application controller;
- cart-related internal routing to Cart Service;
- checkout routing to Checkout Service.

Exact route paths must remain synchronized with the OpenAPI definitions and automated contract tests.

# 11. Apache HTTP Server requirements

Apache HTTP Server must:

- serve the public entry point;
- reverse proxy `/api/*` to the API Gateway;
- preserve correlation and W3C trace headers;
- expose a container health endpoint;
- use a version-pinned upstream image;
- run with only required modules enabled;
- not implement application retries;
- not generate business state;
- emit access logs to stdout and error logs to stderr.

An Apache trace span is not mandatory in the initial release. The first required server span is generated by the API Gateway. Apache must not break the incoming trace context.

# 12. MySQL design

## 12.1 Baseline

- MySQL 8.4 LTS line with an explicit patch tag.
- InnoDB storage engine.
- `utf8mb4` character set.
- `utf8mb4_0900_ai_ci` default collation.
- UTC server and session time zone.
- No application access through the MySQL root account.

## 12.2 Schema separation

| Service | Schema | Application user |
|---|---|---|
| Cart Service | `cart_db` | `cart_app` |
| Checkout Service | `checkout_db` | `checkout_app` |
| Fulfillment Service | `fulfillment_db` | `fulfillment_app` |

Each application user receives privileges only on its schema. Cross-schema reads by application services are forbidden.

## 12.3 Minimum tables

### `cart_db.cart`

- `cart_id` UUID string, primary key;
- `journey_id` UUID string, unique index;
- `status`;
- `created_at`;
- `updated_at`.

### `checkout_db.orders`

- `order_id` UUID string, primary key;
- `journey_id` UUID string, unique index;
- `cart_id` UUID string;
- `payment_authorization_id`;
- `status`;
- `created_at`;
- `updated_at`.

### `fulfillment_db.fulfillment`

- `fulfillment_id` UUID string, primary key;
- `order_id` UUID string, unique constraint;
- `journey_id` UUID string, unique index;
- `status`;
- `created_at`;
- `updated_at`.

All schema changes are versioned through service-owned Flyway migrations. Flyway must migrate a blank database automatically and must fail startup on migration checksum conflicts.

## 12.4 Transactions and pooling

- Transactions remain local to one service and one schema.
- No XA or distributed transaction is allowed.
- HikariCP pool sizes are explicit and low for the test workload.
- JDBC connection, query and transaction timeouts are explicit.
- MySQL readiness executes a real `SELECT 1`.

# 13. RabbitMQ design

## 13.1 Topology

| Object | Name |
|---|---|
| Exchange | `commerce.orders` |
| Exchange type | `topic` |
| Routing key | `order.created` |
| Queue | `commerce.fulfillment` |
| Dead-letter exchange | `commerce.orders.dlx` |
| Dead-letter queue | `commerce.fulfillment.dlq` |

Declarations must be durable and idempotent.

## 13.2 Message contract

The order message contains:

- schema version;
- message ID;
- run ID;
- journey ID;
- order ID;
- cart ID;
- payment authorization ID;
- creation timestamp;
- scenario name and applied flag where required for Fulfillment testing.

Message properties carry:

- `message_id`;
- `correlation_id` set to the journey ID;
- `content_type = application/json`;
- `delivery_mode = persistent`;
- W3C `traceparent`;
- optional `tracestate` and approved baggage.

## 13.3 Reliability rules

- Publisher confirms are mandatory.
- A publish is successful only after positive broker confirmation.
- Consumer acknowledgement is manual.
- The consumer sends ACK only after the fulfillment transaction commits.
- Initial consumer prefetch is `1`.
- Fulfillment processing is idempotent through the unique `order_id` constraint.
- Reject/requeue behavior is scenario-specific and bounded.
- Poison messages go to the dead-letter queue; no infinite redelivery loop is allowed.

# 14. Failure scenarios

Only one scenario is configured at a time. `SCENARIO_ENABLED=false` causes the normal path even when a non-normal scenario name is configured.

| Scenario | Injection point | Required behavior |
|---|---|---|
| `NORMAL` | None | Full journey completes |
| `DB_SLOW` | Checkout MySQL operation | Real delayed query; workflow succeeds |
| `BE_ERROR` | Checkout before DB read | Checkout and Gateway return HTTP 500; no later dependencies |
| `DB_TIMEOUT` | Checkout MySQL operation | Real JDBC/query timeout; HTTP 504; no RabbitMQ publish |
| `MERCHANT_TIMEOUT` | Merchant HTTP call | Client timeout; HTTP 504; no RabbitMQ publish |
| `BROKER_UNAVAILABLE` | RabbitMQ publish | Publish confirm missing/negative or connection unavailable; HTTP 503; no consumer |
| `FULFILLMENT_ERROR` | Fulfillment processing | Message received; failure recorded; no successful fulfillment completion |

Unexpected coding, configuration, Docker, migration or instrumentation failures are internal failures and must not be reported as synthetic scenarios.

## 14.1 Fault activation

Scenario configuration is externalized through environment variables or application configuration:

- `SCENARIO_NAME`;
- `SCENARIO_ENABLED`;
- `DB_SLOW_DURATION_MS`;
- `DB_OPERATION_TIMEOUT_MS`;
- `MERCHANT_TIMEOUT_MS`;
- `BROKER_PUBLISH_TIMEOUT_MS`;
- `FULFILLMENT_ERROR_AFTER_MS`.

The Journey Generator propagates the selected scenario. A service applies a scenario only when it owns the defined injection point.

# 15. OpenTelemetry requirements

## 15.1 Instrumentation

All Java processes use the OpenTelemetry Java Agent as the default instrumentation mechanism. Manual spans are allowed only when a required business operation is not represented by supported automatic instrumentation.

Manual instrumentation must not duplicate HTTP server, HTTP client, JDBC or RabbitMQ spans already produced by the agent.

## 15.2 Required configuration

Each Java container supplies:

- unique `OTEL_SERVICE_NAME`;
- common `service.namespace=commerce-synthetic`;
- `deployment.environment.name=test` for Jaeger tests;
- application version;
- `OTEL_PROPAGATORS=tracecontext,baggage`;
- `OTEL_TRACES_SAMPLER=always_on` for the initial test phase;
- OTLP endpoint and protocol;
- Java Agent path through JVM options.

## 15.3 Sensitive data

The following must not be captured in spans or logs:

- passwords and tokens;
- full authorization headers;
- JDBC credentials;
- complete request or response bodies;
- payment data;
- RabbitMQ credentials;
- unrestricted SQL bind values.

Health and readiness endpoints should be excluded from business trace analysis and may be excluded from tracing if supported cleanly.

# 16. Jaeger test package

Jaeger is included only in `compose.test.yaml` and is started with the test profile. It receives OTLP from all Java services.

Expected test interfaces:

- OTLP/gRPC on container port 4317;
- OTLP/HTTP on container port 4318 when required;
- Jaeger UI and query interface on container port 16686.

Jaeger storage is ephemeral. The test suite must never depend solely on manual UI inspection. The containerized test runner queries Jaeger programmatically and produces a test report.

# 19. Multi-stage Dockerfile

A shared parameterized Dockerfile builds each Java component.

## 19.1 Stages

### Stage 1: dependencies

- Maven image with JDK 21;
- copy parent and module POM files first;
- resolve dependencies;
- use a Docker BuildKit cache mount for Maven artifacts.

### Stage 2: build and test

- copy source code;
- select the Maven module through a build argument;
- execute compilation and unit tests;
- execute configured static analysis;
- package the executable JAR.

### Stage 3: runtime

- minimal JRE 21 image;
- non-root user;
- application JAR;
- version-pinned OpenTelemetry Java Agent;
- no Maven, compiler, source tree or build cache;
- OCI image labels;
- explicit JVM memory and shutdown configuration;
- Actuator-compatible health check where applicable.

## 19.2 Image requirements

- Base images use explicit patch versions and preferably digests.
- No image uses the `latest` tag.
- Runtime processes execute as non-root.
- Images contain no credentials.
- Images support `SIGTERM` and graceful shutdown.
- Images publish OCI source, revision, version and creation labels.
- Final images are independently tagged and pushed.
- The build generates an SBOM.
- A vulnerability scan is a release gate.

## 19.3 Published images

- `commerce/api-gateway:<version>`;
- `commerce/cart-service:<version>`;
- `commerce/checkout-service:<version>`;
- `commerce/merchant-service:<version>`;

# 22. Phase-one exit criteria

All criteria are mandatory unless explicitly waived and recorded.

## Gate 1: clean containerized build

- A clean VM with only Docker, Compose and Git can execute `make test`.
- No JDK or Maven is required on the host.
- Every Maven module compiles.
- Unit tests and static analysis pass.
- All application images build successfully.
- No application image runs as root.

## Gate 2: stack startup

- `docker compose -f compose.yaml -f compose.test.yaml up` starts the complete test stack.
- No container remains in a restart loop.
- All readiness checks become healthy within 120 seconds.
- MySQL readiness executes a real SQL query.
- RabbitMQ accepts AMQP connections.
- Jaeger accepts OTLP.
- The Journey Generator does not start business traffic before readiness.

## Gate 3: scheduling

- Default interval is 10 seconds.
- The interval is configurable without recompilation.
- Scheduling uses fixed delay.
- No more than one initial journey request is active.
- A subsequent journey does not start earlier than 10 seconds after the preceding synchronous request completes, allowing 100 ms local measurement tolerance.
- No journey is silently dropped.

## Gate 4: normal-flow stability

At least 30 consecutive NORMAL journeys complete without:

- unexpected HTTP responses;
- message loss;
- unplanned redelivery;
- orphan records;
- container restart;
- pool exhaustion;
- unexpected application exceptions.

For every journey:

- cart creation and read succeed;
- payment authorization succeeds;
- order persistence succeeds;
- RabbitMQ confirms the publish;
- fulfillment persistence succeeds;
- consumer ACK occurs after database commit;
- final state is coherent.

## Gate 5: distributed tracing

For every validated journey:

- a single end-to-end trace ID connects the required Java services;
- Gateway, Cart, Checkout, Merchant and Fulfillment have unique `service.name` values;
- HTTP parent-child relationships are valid;
- RabbitMQ producer context reaches the consumer;
- JDBC spans identify MySQL operations;
- no independent trace begins mid-workflow;
- no duplicate spans are caused by overlapping manual and automatic instrumentation;
- synchronous child spans do not outlive their parents;
- required correlation attributes are present and contain no sensitive data.

Additional infrastructure spans are allowed. Acceptance is based on required functional spans and relationships, not a fixed global span count.

## Gate 6: deterministic scenarios

Each non-normal scenario runs successfully at least three consecutive times with the expected result:

- `DB_SLOW`: slow MySQL operation and successful completion;
- `BE_ERROR`: HTTP 500 and prohibited downstream operations absent;
- `DB_TIMEOUT`: real JDBC timeout, HTTP 504 and no publish;
- `MERCHANT_TIMEOUT`: HTTP client timeout, HTTP 504 and no publish;
- `BROKER_UNAVAILABLE`: publish failure, HTTP 503 and no consumer processing;
- `FULFILLMENT_ERROR`: message received, failure visible and successful fulfillment absent.

Jaeger must show error status and exception details on the originating span and propagated failure status where specified.

## Gate 7: RabbitMQ reliability

- Durable exchange, queue and binding exist.
- Messages are persistent.
- Publisher confirms are enabled and tested.
- Consumer ACK is manual and follows MySQL commit.
- Prefetch is 1.
- Normal tests leave no messages ready or unacknowledged.
- Redelivery does not create duplicate fulfillment rows.
- Poison-message handling reaches the DLQ without an infinite loop.

## Gate 8: MySQL integrity

- Flyway migrates every schema from empty state.
- Migration checksum conflicts fail startup.
- Services use dedicated non-root users.
- Cross-schema application access is rejected.
- Required primary keys, unique constraints and indexes exist.
- Restarting an application service does not require database recreation.
- Database records reconcile with completed journeys.

## Gate 9: Jaeger automated validation

- Jaeger is started by the test Compose file.
- The test runner queries Jaeger programmatically.
- Trace validation is automated and not dependent on UI inspection.
- Test reports contain scenario, run ID, journey ID, trace ID, expected result and observed result.
- Jaeger data is disposable after test completion.

## Gate 10: security and release quality

- No secret is committed to Git.
- No secret is present in images, logs, reports or spans.
- No `latest` image tag is used.
- Application images pass the configured vulnerability threshold.
- SBOMs are generated.
- Domain-code unit coverage is at least 80%.
- No blocking or high-severity defect remains open.
- README instructions reproduce build and test on a clean VM.

- MySQL data;
- RabbitMQ data;
- Jaeger data;
- generated test reports unless intentionally published as CI artifacts;
- local IDE state.

# 25. Operational failure classification

| Failure class | Example | Expected treatment |
|---|---|---|
| Configured synthetic scenario | `DB_TIMEOUT` | Expected test result |
| Validation failure | Invalid environment property | Startup failure |
| Dependency readiness failure | MySQL unavailable at boot | Unready, bounded startup failure |
| Internal application defect | Null pointer or invalid state transition | Internal failure, never relabeled as a scenario |
| Telemetry export failure | Jaeger unavailable | Test failure; business result remains separately recorded |
| Trace validation failure | Broken parent-child relationship | Release-blocking test failure |
| Build or image failure | Maven or scan failure | Publication blocked |

# 26. Development sequence

## Increment 1: repository and containers

- Create monorepo and Maven parent.
- Implement shared multi-stage Dockerfile.
- Add Apache, MySQL, RabbitMQ and Jaeger Compose services.
- Implement health checks and Makefile targets.

## Increment 2: normal synchronous path

- Implement Journey Generator, Apache routing, Gateway, Cart, Checkout and Merchant.
- Add MySQL schemas and Flyway migrations.
- Validate HTTP and JDBC traces in Jaeger.

## Increment 3: asynchronous path

- Implement RabbitMQ topology, publisher confirms and Fulfillment consumer.
- Add manual ACK after MySQL commit.
- Validate producer-consumer context propagation.

## Increment 4: fault scenarios

- Implement six non-normal scenarios.
- Add deterministic functional and trace assertions.

## Increment 5: automated exit gates

- Implement Jaeger query validation.
- Add 30-journey stability test and three-run scenario tests.
- Add SBOM, vulnerability scan and registry publication pipeline.

# 27. Definition of done

The initial release is complete only when:

- the entire solution builds, tests and runs in containers;
- the host needs only Docker, Compose and Git;
- the normal workflow and all scenarios satisfy their exit gates;
- Jaeger trace validation is automated;
- MySQL and RabbitMQ reliability requirements pass;
- application images are non-root, scanned, versioned and registry-ready;
- source, Compose files, Dockerfiles, migrations, tests and documentation are present in Git;
- a clean VM can reproduce the test result;
- a separate clean VM can run the registry-published images;
- no blocking or high-severity defect remains.

# 28. Future evolution

After phase-one acceptance, the next observability phase may:

- introduce an OpenTelemetry Collector;
- send OTLP to Dynatrace using `compose.dynatrace.yaml`;
- add metrics and logs;
- add parallel or variable-rate journey generation;
- add circuit breakers or rate limiting;
- implement the transactional outbox pattern;
- migrate the deployment to Kubernetes;
- add Apache-native tracing if required.

These changes must not require redesign of the business contracts, service boundaries or W3C propagation model.
